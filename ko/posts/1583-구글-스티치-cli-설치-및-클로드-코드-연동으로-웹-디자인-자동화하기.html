구글 스티치 CLI 설치 및 클로드 코드 연동으로 웹 디자인 자동화하기

2026년 10월 28일

구글 스티치 CLI를 활용해 터미널 환경에서 클로드 코드(Claude Code)와 연동하면 복잡한 설정 없이도 몇 분 만에 AI 웹 디자인부터 실제 프론트엔드 코드 구축까지 한 번에 끝낼 수 있다.

기존처럼 번거로운 구글 클라우드 콘솔 설정이나 컨텍스트 토큰을 갉아먹는 무거운 MCP 설정에 매달릴 필요 없이, 명령줄 하나로 디자인 에이전트를 자유자재로 다루는 시대가 열린 셈이다.

요즘 AI 코딩 도구들이 하루가 멀다 하고 쏟아져 나오지만, 막상 화면을 만들어보면 결과물이 어딘가 나사 하나 빠진 것처럼 허술할 때가 많았다. 텍스트 프롬프트를 기가 막히게 작성해도 나오는 UI는 어디선가 본 듯한 양산형 부트스트랩 느낌을 벗어나지 못했고, 디테일한 인터랙션을 얹으려면 결국 손으로 코드를 일일이 뜯어고쳐야 했다.

"도대체 언제쯤이면 기획 의도를 제대로 반영한 감각적인 웹사이트가 한 방에 나올까" 싶었는데, 이번에 구글이 내놓은 도구가 그 답답함을 제대로 긁어주었다.

단순히 디자인 시안을 뽑아주는 데 그치지 않고, 클로드 코드가 스티치를 직접 호출해 시안을 수정하고 반응형 검증과 스크롤리텔링 인터랙션까지 스스로 완성해내는 작업 방식을 마주하니 머리를 한 대 세게 맞은 기분이었다.

이번 글에서는 구글 스티치 CLI의 설치부터 핵심 연동 과정, 그리고 실제 실무에서 뻔하지 않은 완성도 높은 결과물을 뽑아내는 전체 파이프라인을 낱낱이 파헤쳐 본다.

구글 스티치 CLI 출시 배경과 클로드 코드 연동의 필연성

기존 MCP 설정의 치명적인 한계와 토큰 낭비

기존에 구글 스티치(Stitch)를 AI 에이전트와 연동하려 해본 사람이라면 누구나 한 번쯤 뒷목을 잡았을 것이다. MCP(Model Context Protocol) 서버를 연결하는 과정 자체가 구글 클라우드 플랫폼(GCP)에서 수많은 권한을 설정하고 인증 키를 발급받아야 하는 고역이었기 때문이다.

개발자가 코드를 짜고 디자인을 하기도 전에 인프라 세팅 단계에서 진이 다 빠져버리는 기형적인 구조였다.

더 심각한 문제는 컨텍스트 토큰의 상시 점유였다. MCP 방식은 에이전트 세션이 유지되는 내내 도구의 스키마와 정의를 컨텍스트 윈도우 안에 띄워두어야 한다.

Anthropic의 Claude 요금 정책상 대화가 길어지고 읽어 들이는 파일 수가 많아질수록 5시간 단위의 순환 한도와 비용 소모는 걷잡을 수 없이 부어난다. 도구를 쓰지도 않는 순간조차 귀중한 컨텍스트 공간을 낭비하고 있었던 셈이다.

비싼 구독료를 내면서도 정작 중요한 비즈니스 로직을 다룰 토큰이 부족해지는 어처구니없는 상황이 반복되었다.

구글 스티치 CLI의 등장은 바로 이 지점을 완벽하게 저격했다. "Claude only loads the tool into context when it actually needs it, unlike MCP which stays in the context all the time."이라는 평가처럼, 에이전트가 실제로 디자인을 요청하거나 수정할 때만 도구를 메모리에 로드한다.

실제로 최근 구글의 발표와 실무 테스트 결과에 따르면, 새로운 제너레이티브 UI 접근법이 기존 전통적 웹 디자인 방식보다 90%에 달하는 높은 확률로 더 직관적이고 완성도 높은 결과물을 만들어낸다고 한다.

불필요한 고정 비용을 원천 차단하고 작업 속도를 획기적으로 끌어올린 실용적인 진화다.

스티치 단독 사용의 딜레마와 에이전트 결합의 가치

스티치 자체는 구글의 제미나이(Gemini) 모델을 기반으로 텍스트나 간단한 스케치를 고해상도 UI로 바꿔주는 륭한 디자인 생성 툴이다. 브라우저에서 모바일이나 웹 뷰를 고르고 프롬프트를 넣으면 깔끔한 컴포넌트가 뚝딱 나온다.

하지만 딱 거기까지였다. 화면 안에서 정적으로 멈춰 있는 시안일 뿐, 이를 실제 제품으로 변환하려면 개발자가 눈으로 보고 코드로 베껴 쓰는 노가다를 피할 수 없었다.

게다가 스티치는 독립된 웹 앱이기 때문에 자체적으로 커스텀 스킬이나 확장 기능을 품을 수 없다. 반면 클로드 코드는 다양한 스킬을 주입받아 터미널에서 프로젝트 전체를 제어할 수 있는 두뇌를 지녔다.

스티치라는 날카로운 붓과 클로드 코드라는 숙련된 화가가 만났을 때 비로소 진정한 자동화 파이프라인이 완성되는 것이다.

서로 다른 생태계의 도구가 결합하면서 생기는 시너지는 상상 이상이었다.

실제로 "Using the two together made designing so much better, and your designs don't look like everyone else's anymore."라는 반응이 나오는 이유가 여기에 있다.

에이전트가 스티치 주변에 다양한 커스텀 도구들을 유기적으로 배치함으로써, 천편일률적인 AI 특유의 껍데기 디자인을 완전히 탈피할 수 있게 되었다.

구글 스티치 CLI 설치 및 5분 퀵스타트 세팅법

터미널 명령어 기반의 Stitch CLI 설치와 계정 인증

설치 과정은 놀라울 정도로 단순하다. 복잡한 클라우드 콘솔 화면을 전전할 필요 없이 평소 개발하듯 터미널 창을 열고 몇 줄의 명령어만 입력하면 끝난다.

전역 환경에 패키지를 깔아주기 위해 아래 명령어를 실행하는 것으로 시작한다.

npm install -g @google/stitch 명령어를 입력하면 순식간에 설치가 완료된다. 설치가 정상적으로 끝났는지 확인하기 위해 stitch --help를 쳐서 버전과 사용 가능한 서브 커맨드들이 출력되는지 점검한다.

"This CLI is much easier to set up and will show you how in a bit."이라는 설명이 결코 빈말이 아님을 체감할 수 있는 대목이다.

그다음은 계정 인증 단계다. stitch login 명령어를 터미널에 입력하면 기본 웹 브라우저가 자동으로 실행되면서 구글 로그인 창이 뜬다.

브라우저에서 로그인을 완료하면 로컬 머신의 인증 정보 파일인 credentials.json에 토큰이 안전하게 저장된다. 엔터프라이즈 환경에서 요구하는 까다로운 IAM 역할 설정 없이도, 개인 개발자가 즉각적으로 구글 인프라의 디자인 생성 엔진을 활용할 수 있는 권한을 얻게 되는 것이다.

에이전트 스킬 주입과 폴더 경로 설정의 결정적 디테일

CLI 도구와 인증이 준비되었다면, 이제 클로드 코드가 이 도구를 인지하고 자유자재로 다룰 수 있도록 '스킬(Skills)'을 심어주어야 한다. 이 단계에서 가장 중요한 핵심 포인트가 바로 폴더 경로 지정이다.

많은 사용자가 이 부분을 간과해 도구가 제대로 로드되지 않는 문제로 삽질을 겪곤 한다.

반드시 실행해야 하는 명령어는 stitch agent-skills add --dir .claude/skills다. "If you don't mention the `.claude` folder, it won't be able to load skill when you prompt it and would only look for it when you ask it in your prompt."이라는 경고처럼, 클로드 코드는 기본적으로 프로젝트 루트의 .claude 디렉터리 내부만을 스킬 저장소로 탐색하기 때문이다.

경로를 명시하지 않고 엉뚱한 곳에 설치하면 에이전트는 스티치의 존재 자체를 인지하지 못한다.

명령어가 성공적으로 실행되면 .claude/skills 디렉터리 내부에 스티치 관련 파일들이 자리를 잡는다. 여기에는 에이전트가 색상, 타이포그래피, 컴포넌트 규칙을 일관되게 해석할 수 있도록 돕는 design.md 가이드 파일과 다양한 프롬프트 키워드 세트가 포함되어 있어, 생성되는 웹페이지의 스타일 파편화를 사전에 방지해 준다.

📊 숫자로 보면

기존 브라우저 기반 수동 디자인 추출 방식 대비, CLI를 통한 스킬 자동 주입 시 초기 세팅 시간이 평균 30분 이상에서 단 3분 이내로 90% 이상 단축된다. 특히 컨텍스트 토큰을 상시 점유하던 MCP 대비 API 호출 시점의 온디맨드 로딩 방식을 통해 세션당 소모되는 고정 프롬프트 토큰을 수천 개 이상 절약할 수 있다.

아이디어 구체화와 brief.md를 통한 디자인 방향성 수립

단발성 프롬프트의 실패와 심층 인터뷰의 필요성

AI를 활용해 웹사이트를 만들 때 사람들이 가장 흔히 범하는 실수는 "우주 테마의 멋진 랜딩 페이지 만들어줘" 같은 모호한 프롬프트 한 줄을 툭 던지는 것이다. 이렇게 시작하면 AI는 세상에서 가장 평범하고 뻔한 결과물을 내놓는다.

사용자의 머릿속에 있는 감정선, 정보의 우선순위, 브랜드의 철학이 전혀 전달되지 않았기 때문이다.

이를 극복하기 위해 클로드 코드에게 사용자를 취재하듯 심층 인터뷰를 진행하라는 역할을 부여해야 한다. "I want to make a site for space...

so for that you need to interview me and get the general idea on how I want the site to be like and how I want it to tell the story and keep on interviewing until it gets the idea, use askquestion tool to ask me questions and then combine the flow in a file brief.md"와 같은 형태로 프롬프트를 구성하는 방식이다.

에이전트가 사람에게 끝없이 되물으며 사이트의 목적, 타깃 독자, 감정의 기승전결을 끄집어내게 만든다.

이 대화형 질의응답 과정을 거쳐 모호했던 콘셉트는 구체적인 기획서 형태로 탈바꿈한다. 인간 기획자와 디자이너가 킥오프 미팅에서 치열하게 의견을 나누듯, 에이전트와의 인터뷰를 통해 뼈대를 단단하게 다지는 작업이 선행되어야만 뒤따르는 모든 디자인 단계가 흔들리지 않는다.

brief.md 파일이 디자인 일관성을 지키는 메커니즘

인터뷰가 완료되면 클로드 코드는 정리된 모든 논리를 brief.md라는 단일 파일로 엮어 프로젝트 루트에 저장한다. 이 파일은 단순한 메모장이 아니라, 향후 스티치가 수많은 시안과 변형을 만들어낼 때 길을 잃지 않게 붙잡아주는 '단 하나의 진실 공급원(Single Source of Truth)' 역할을 수행한다.

스티치로 여러 화면을 뽑다 보면 제미나이 모델의 특성상 세션마다 버튼의 둥글기나 폰트 패밀리, 심지어는 전체적인 톤앤매너가 제멋대로 튀는 현상이 잦다. 하지만 brief.md가 명확한 앵커 역할을 해주면, 클로드 코드가 스티치에 프롬프트를 보낼 때마다 이 문서의 가이드라인을 참조하여 엄격한 일관성을 요구하게 된다.

스타일 붕괴 현상을 시스템적으로 틀어막는 가장 확실한 안전장치다.

기획이 문서화되어 로컬 파일로 박혀 있는 것과 단순 프롬프트 창에 휘발성으로 남아 있는 것은 하늘과 땅 차이다. 팀 내 협업에서도 이 마크다운 문서는 훌륭한 디자인 명세서 역할을 겸하게 되며, 차후 유지보수 시에도 원래 의도를 추적할 수 있는 훌륭한 나침반이 되어준다.

반복 생성과 코드 변환으로 완성하는 인터랙티브 사이트

8번의 수정을 거치는 자율 피드백 루프와 디자인 변형

기획이 준비되면 본격적으로 스티치 CLI를 가동한다. "use the brief.md as a guide, and use stitch cli to prompt it to build the landing page, and ask stitch to generate variants"라는 지시를 내리면, 클로드 코드가 스스로 스티치 프로젝트를 생성하고 여러 가지 레이아웃 변형(Variants)을 요청한다.

흥미로운 점은 클로드 코드가 스티치의 첫 번째 결과물을 결코 맹신하지 않는다는 것이다. 실제로 진행된 프로젝트 사례를 보면 Claude는 무려 8개의 디자인 버전을 연속으로 뽑아내며 점진적으로 완성도를 높였다. "매번 Claude가 디자인 문제를 발견할 때마다 Stitch에 새로운 디자인을 요청했습니다."라는 기록처럼, 시각적인 어색함이나 여백의 불균형을 에이전트가 자체적으로 감지하고 다시 렌더링을 지시한 결과다.

사람이 일일이 화면을 보고 "여기 고쳐줘"라고 말하지 않아도 에이전트들끼리 티키타카를 주고받으며 퀄리티를 끌어올린다.

준비된 결과물은 스티치 내부 뷰어를 통해 PC 데스크톱 화면과 모바일 뷰포트에서 즉각 확인이 가능하다. 하지만 스티치가 뽑아낸 원본은 어디까지나 정지된 평면 이미지일 뿐이다.

진정한 의미의 웹사이트가 되려면 이를 살아 숨 쉬는 웹 기술(HTML, CSS, React)로 변환하는 빌드 단계가 필수적이다.

에셋 다운로드부터 프론트엔드 코드 자동 구축까지

디자인이 최종 확정되면 클로드 코드는 스티치의 신규 도구를 호출해 모든 시안 데이터, 사용된 고해상도 이미지, 커스텀 웹 폰트 에셋을 로컬 프로젝트 폴더로 일괄 다운로드한다. 스티치 CLI가 화면을 단순 캡처가 아닌 구조화된 웹페이지 및 이미지 형식으로 에이전트에 넘겨주기 때문에 가능한 일이다.

에이전트는 내려받은 자원들을 분석해 컴포넌트 단위로 코드를 작성하기 시작한다. 브라우저에서 로컬 호스트를 열어보면 스티치 뷰어에서 정적으로 보았던 디자인이 실제 돔(DOM) 요소로 완벽히 재현되어 나타난다.

더욱 놀라운 것은 원본 디자인에는 없었던 이미지에 마우스를 올렸을 때의 줌인 효과나 미세한 페이드인 전환 같은 인터랙션을 클로드 코드가 센스 있게 덧붙여 놓는다는 점이다.

정적 목업이 단 몇 분 만에 인터랙티브 프로토타입으로 거듭나는 순간이다.

다만 아무리 기술이 발전했어도 생성형 AI의 한계는 분명히 존재한다. UX Pilot이나 v0 같은 도구들이 멀티 스크린 플로우나 즉각적인 코드 내보내기에 최적화되어 있듯, 스티치 역시 첫 빌드 상태에서는 예기치 못한 스타일 충돌이나 반응형 깨짐이 발생할 수 있다.

그렇기에 이를 사후 검증하는 전용 스킬들의 배치가 반드시 뒤따라야 한다.

🔥 맹신이 낳는 반응형 파괴의 함정

스티치가 뽑아내는 화려한 데스크톱 뷰에 취해 검증을 건너뛰면 모바일 환경에서 텍스트가 겹치거나 가로 스크롤이 터지는 대참사가 일어난다. 정적인 시안과 실제 렌더링 엔진 사이의 간극을 메우지 않는 AI 도구 연동은 그저 예쁜 쓰레기를 양산할 뿐이다.

반드시 기기별 뷰포트 캡처와 코드 단위의 반응형 리뷰 파이프라인을 구축해 강제 검증해야 한다.

전문 스킬 결합을 통한 완성도 극대화 전략

Stitch Review 스킬을 활용한 기기별 반응형 시각 검증

데스크톱 기준으로 아름답게 뽑힌 사이트라 할지라도 모바일이나 태블릿에서 박살 난다면 상용 서비스로 쓸 수 없다. 스티치 자체는 아직 단일 워크플로우 안에서 다양한 브레이크포인트 레이아웃을 완벽하게 계산해 내지 못하기 때문에, 이를 보완하기 위해 Stitch-review 스킬을 파이프라인에 투입한다.

이 스킬의 작동 방식은 매우 직관적이면서도 강력하다. 모바일, 태블릿, 데스크톱 등 다양한 화면 해상도에서 헤드리스 브라우저로 실제 스크린샷을 찍은 뒤, 원본 디자인과 픽셀 단위로 대조한다.

그 후 Claude는 종합 보고서를 출력하는데, "보고서는 모든 화면 크기를 다루며, 가장 심각한 문제부터 나열합니다."라는 말 그대로 치명적인 레이아웃 오류를 우선순위대로 정리해 낸다.

보고서가 나오면 에이전트는 즉시 CSS 미디어 쿼리를 손질하며 디자인과의 오차를 메워나간다.

물론 짚고 넘어가야 할 명확한 기술적 한계도 존재한다. "리뷰 스킬은 시각적인 일치 여부만 확인할 뿐, 사이트의 동작이나 향후 발생할 오류를 예측하지는 못합니다."

시각적 오차는 잡을 수 있어도 자바스크립트의 비동기 로직 충돌이나 브라우저 렌더링 성능 저하까지 미리 내다보지는 못하므로, 프로덕션 배포 전 인간 개발자의 성능 프로파일링이 병행되어야만 한다.

스크롤리텔링과 Story Review로 살려내는 사이트의 서사

시각적 정렬이 끝났다면 이제 사이트에 생명력을 불어넣을 차례다. 정적인 웹페이지에 서사를 부여하기 위해 스크롤리텔링(Scrollytelling) 스킬을 적용한다.

사용자가 스크롤을 내릴 때마다 콘텐츠가 단순히 아래에서 위로 밀려 올라오는 것이 아니라, 장면이 전환되듯 시각 요소들이 유기적으로 반응하도록 만드는 기법이다.

우주 탐사 콘셉트의 사이트라면 로켓이 발사될 때 화면에 미세한 흔들림(shake) 효과를 주고, 스크롤 깊이에 따라 배경의 별들이 시차(Parallax)를 두고 움직이게 하거나 역사적 타임라인 구간에서는 화면이 가로로 매끄럽게 슬라이드 되도록 구현한다. "애니메이션은 단순히 시각적 화려함을 넘어, 사용자의 몰입감을 높이고 이야기를 전달하는 핵심 도구입니다."라는 관점이 코드에 그대로 반영되는 것이다.

앞서 적용한 리뷰 스킬 덕분에 이러한 복잡한 애니메이션 역시 모바일 기기에서 깨짐 없이 부드럽게 작동한다.

하지만 과유불급이라는 말처럼, 애니메이션이 남발되면 방문자는 멀미를 느끼고 피로해진다. 이를 걸러내기 위해 마지막으로 Story-review 스킬을 돌린다.

프롬프트에 "호스트 Awwwards 심사위원처럼 행동하여 사이트를 엄격하게 평가하라"고 강력하게 페르소나를 부여하면, 에이전트는 스토리 전개가 자연스러운지, 인터랙션 속도가 콘텐츠 가독성을 해치지는 않는지 가차 없이 메스를 댄다.

불필요하게 요란한 모션을 걷어내고 완벽하게 정제된 사용자 경험(UX)만이 남게 된다.

💭 개인적인 생각

구글 스티치 CLI와 클로드 코드의 결합을 직접 돌려보면서, 우리가 흔히 말하던 '개발의 종말'이나 '디자인의 대체'라는 담론이 얼마나 피상적이었는지를 다시금 실감했다. 도구가 아무리 강력해져도 "어떤 이야기를 어떤 감정으로 전달할 것인가"를 정의하는 인터뷰 단계와, 과도한 시각적 공해를 쳐내는 Awwwards 수준의 엄격한 리뷰 기준을 세우는 것은 결국 사람의 몫이다.

과거 윤석열 씨 재임 시절 R&D 예산을 무분별하게 삭감하며 기술 생태계의 기초체력을 흔들어놓았던 황당한 퇴행을 기억한다. 기술 혁신은 단순히 유행하는 툴을 가져다 쓰는 데서 오는 게 아니라, 도구를 다루는 기획자의 깊이 있는 시각과 탄탄한 생태계 지원 속에서 꽃을 피운다.

AI가 손발이 되어 시안을 치고 코드를 짜주는 지금이야말로, 우리는 도구 너머의 본질적인 기획과 철학에 더 매달려야 한다.

❓ 자주 묻는 질문

Q. 구글 스티치 CLI 설치 및 클로드 코드 연동 방법은 무엇인가요?

터미널에서 npm install -g @google/stitch 명령어로 CLI를 전역 설치한 뒤, stitch login을 실행하여 브라우저에서 구글 계정으로 인증을 완료한다. 이후 반드시 stitch agent-skills add --dir .claude/skills 명령어를 입력해 클로드 코드가 인식할 수 있는 전용 디렉터리에 스티치 스킬을 주입해주면 즉시 연동되어 사용할 수 있다.

Q. Stitch CLI를 사용하면 기존 MCP 방식보다 무엇이 더 좋아지나요?

기존 구글 클라우드 콘솔에서 복잡하게 거쳐야 했던 권한 설정과 인증 절차가 명령어 몇 줄로 대폭 간소화된다. 또한 세션 내내 컨텍스트 윈도우를 차지호던 MCP와 달리, 스티치 CLI는 클로드 코드가 디자인 생성을 요청할 때만 온디맨드로 로드되므로 컨텍스트 토큰 소모를 크게 줄이고 비용 효율성을 극대화할 수 있다.

Q. AI 에이전트로 웹사이트 디자인을 자동화하는 워크플로우가 궁금해요.

먼저 클로드 코드에게 사용자 심층 인터뷰를 진행하도록 프롬프트하여 사이트의 콘셉트와 서사가 담긴 brief.md 문서를 생성한다. 그다음 스티치 CLI를 호출해 8회 이상의 반복 수정을 거치며 최적의 디자인 버전을 도출하고, 이를 실제 코드로 변환한 뒤 Stitch-review와 Story-review 스킬을 통해 반응형 뷰포트와 인터랙션을 엄격히 검증하여 완성도를 높인다.

이 포스팅은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

구글 스티치 CLI와 클로드 코드의 결합은 단순한 디자인 생성 툴의 업데이트를 넘어, 아이디어가 제품 코드로 직결되는 방식 자체를 근본적으로 뒤흔들고 있다. 복잡했던 설정의 장벽이 허물어지고 에이전트가 디자인의 생성과 검증, 고도화까지 스스로 피드백 루프를 돌리는 워크플로우는 이제 선택이 아닌 필수가 되어가고 있다.

도구의 편의성에 안주해 뻔한 결과물을 찍어낼 것인가, 아니면 스킬의 조합과 집요한 기획으로 남들과 전혀 다른 몰입형 경험을 만들어낼 것인가는 전적으로 엔지니어이자 크리에이터인 우리의 손끝에 달려 있다.

지금 당장 터미널을 열고 스티치 CLI를 설치해 당신만의 독창적인 사이트를 빌드해보길 권한다.

결국 도구를 지배하는 것은 얼마나 명확한 철학으로 AI를 심문하느냐에 달려 있지 않을까.
